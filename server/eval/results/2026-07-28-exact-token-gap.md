# #188 — lexical exact-token assist: MEASURED OUT (park)

**Date**: 2026-07-28 · **Decision**: **PARK** · **Pre-registration**: spec v3 §5,
sha256 `f2dba8db519a69f2…`, committed at `3da11fa` **before any number was observed**.

**Headline: the premise is false.** There is no exact-token retrieval gap in UM's corpus.
There *is* a large **long-document** gap, which is a different problem with a different
(and cheaper) fix.

---

## 1. What was measured

A bit-identical clone of the live 279-point `memories` collection (vectors copied, nothing
re-embedded) into a local **qdrant 1.7.3** — the production version — scored against 109
identifiers drawn mechanically by a frozen regex, each with **set-valued relevance** (every
document containing it). Two query shapes per identifier, over identical targets in an
identical haystack:

- **exact-token**: `what is <identifier>` — #188's query class
- **semantic**: a paraphrase generated by an LLM **blind to the hypothesis**, identifier absent

Scoring: `recall@5` by document id, deterministic, **no LLM judge**. Two runs.

## 2. Results

`recall@5`, run 1 / run 2:

| Stratum | n | vector (exact) | vector (semantic) | fusion_deployable (exact) |
|---|---|---|---|---|
| **fact** | 32 | **1.000** | **1.000** | 1.000 |
| **doc** | 77 | **0.104** | **0.091** | **0.805** |
| combined | 109 | 0.367 / 0.367 | 0.358 / 0.349 | 0.862 / 0.862 |

## 3. Why the premise is false

**Exact-token phrasing costs nothing.** On identical targets, `what is <identifier>` and a
paraphrase that never mentions the identifier retrieve *equally well* — delta **0.000** in the
fact stratum and **−0.013** in the doc stratum. The Cerebras argument (embeddings retrieve
topical neighbors instead of the exact match) does not reproduce here.

A pipeline-health probe that reads no gate confirms it independently: querying with an
identifier **alone** returns its document at **recall@5 = 1.000** (16/16 short facts), and
verbatim document text retrieves itself at **rank 1, 20/20**. `text-embedding-3-small` handles
rare identifier tokens well at this corpus scale.

**The kickoff's premise was right, and stronger than expected.** "Fact-sized normalized texts,
not raw transcripts — the gap may be far smaller than in Cerebras' thread corpus." Measured, the
gap on fact-sized memories is **exactly zero**: vector recall is 1.000 on both phrasings.

## 4. The real finding: long documents are nearly unretrievable

**Doc-sized session summaries retrieve at ~0.10 regardless of how you query them** — a **10×**
gap versus the 1.000 of fact-sized memories, for identical query shapes. 34% of the corpus (96
of 279 points, median 1,278 chars, max 5,099) is effectively invisible to vector search.

The cause is dilution, not phrasing: a 1,278-character summary compressed into one 1,536-dim
vector is saturated, so no single query — exact-token *or* semantic — sits close enough to
retrieve it.

The lexical arm does fix it (**+0.701** in the doc stratum; **54 rows gained, 0 lost** in both
runs), because lexical matching does not saturate with length. But it compensates downstream for
a cause that is upstream.

### Which remedy this implicates (spec §8, mandatory under either outcome)

**Chunking doc-sized summaries at write time.** §8 pre-registered this as the cheaper competing
remedy *if* the gap turned out to be doc-only dilution, and that is exactly what it is. Chunking
addresses the cause — one vector per coherent span instead of one per 1,278-char document — and
needs no second ranker, no fusion, and no read-path change. A lexical assist would mask a
write-path modelling problem behind read-path machinery.

The descriptive `keyword_exact` arm scored **1.000** on exact-token queries, but that is
tautological (exact substring match on the identifier is how relevance is defined) and carries no
evidential weight.

## 5. Protocol deviations (both recorded, both made before any gate was read)

1. **The exact-token arm was re-operationalized** from `semantic + identifier` to
   `what is <identifier>`. The frozen v3 rule appended the identifier to the blind semantic query
   to form a strict minimal pair; run 1 showed that construction cannot express #188's premise —
   appending a token to a rich paraphrase yields a query *more* informative than the semantic
   form, and vector results were byte-identical across both phrasings on 109/109 rows. The
   correction makes the gates **harder** to pass, so it is instrument repair, not tuning.
2. **MatchText narrows on rare tokens, not all tokens.** qdrant's `MatchText` is AND-over-tokens,
   so requiring every token of a 7-word natural query is unsatisfiable — the deployable arm
   returned empty on **218/218** queries in run 1. §7.2 always said "the query's *rare* tokens";
   the frozen §5.5 selector line failed to encode it. Rare = top-3 by IDF among tokens with
   df ≤ 20% of the collection.

Both were found by the pipeline-health probe and the negative controls, neither of which reads a
gate.

**The frozen §5 was NOT edited to match.** Doing so would forge the pre-registration. §5 remains
byte-identical to what was hashed and committed at `3da11fa`; the deviations are recorded in spec
**§11**, deliberately placed after §6 so it falls outside the hashed byte range. The anchor still
verifies: sha256 of the §5 range = `f2dba8db519a69f2…`, unchanged.

## 6. The pipeline-health floor fired — its premise was wrong, and the instrument is now fixed

The original a-priori floor (semantic vector `recall@5 ≥ 0.50`, corpus-wide) failed at
0.358/0.349. It was **not** overridden. Investigation showed the floor's own assumption was wrong,
on two independent pieces of evidence: verbatim text retrieves at rank 1 (20/20), and the fact
stratum scores a clean 1.000. The corpus-wide average is dragged below 0.50 by the doc stratum's
genuine 0.091 — the finding, not a fault.

A recall floor was simply the wrong instrument: it encodes an assumption about *blind-query
quality* and is dragged down by whichever stratum genuinely retrieves worst. **The harness now
uses:**

1. **A direct verbatim probe** — a document's own text must retrieve that document at rank 1
   (floor 0.90). It uses no generated query, so it separates "retrieval is broken" from "these
   queries are vague", which is exactly the confusion the old floor could not resolve.
2. **Per-stratum floors** — `fact ≥ 0.50`; `doc` reported with **no floor asserted**, so a
   genuinely-hard stratum can neither mask nor manufacture a fault.

Both runs below were produced with the corrected instrument: **verbatim probe 20/20 (1.000)
HEALTHY**, `health[fact] 1.000 ≥ 0.50`, `health[doc] 0.091 / 0.078` reported, overall
`pipelineHealth.ok = true`. The verdict is unchanged — G1a fails identically — so the fix altered
the instrument's honesty, not the result.

## 7. Negative controls (asserted every row, both runs)

- Lexical weight 0 reproduced the vector ranking **exactly, row for row** — 218/218 queries.
- The lexical arm was empty on 94–95 of 109 semantic queries, so G3's pass is **weakly
  evidenced**: on identifier-free queries the deployable arm mostly degrades to vector-only and
  cannot displace anything. Recorded rather than credited.

## 8. What would change this decision

- A corpus where fact-sized memories stop retrieving at 1.000 (much larger, or many
  near-duplicate identifiers).
- Evidence that exact-token queries are a meaningful share of real traffic — **currently
  unmeasurable**: `recall.search` is a bare counter (`lib/stats.mjs:155`), 7 days of Pi logs hold
  zero query-bearing lines, and the one automatic search per session posts the **raw prompt text**
  (`user-prompt-submit.sh:7`), which is semantic by construction.
- Adopting chunking first and re-measuring: if chunking closes the doc gap, a lexical arm has
  nothing left to fix.

## 9. Disposition

- `#188` **parked / measured out.** No lexical assist, no fusion, no flag shipped. No retrieval
  code was written — the serving path is untouched.
- Harness and pure libs are committed as durable instruments: the next retrieval idea gets a
  ready-made exact-token measurement.
- **Follow-up worth its own issue**: long-document retrieval dilution — 34% of the corpus at
  ~0.10 recall — with write-time chunking as the leading candidate.

Joins [`#130`](../../../docs) (no-answer floor) and `#133` (bouncer) as a measured negative that
prevented a bad ship. In all three the eval-gate did its job; here it also surfaced a larger real
problem than the one it was pointed at.
